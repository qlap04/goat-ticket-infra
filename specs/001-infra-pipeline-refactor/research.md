# Phase 0 Research: Infrastructure Repository & Pipeline Refactor

No `[NEEDS CLARIFICATION]` markers remain in the spec, and the Technical Context has no open unknowns. This document instead records the design decisions needed to turn the spec's requirements into a concrete structure, since several requirements (parameterized dev/prod, consolidated stage, array-driven RBAC, shared network rules) admit more than one reasonable implementation shape.

## 1. Folder reorganization mapping

- **Decision**: Create `deploy/bicep/`, `deploy/pipeline/`, `deploy/script/`, `deploy/variables/`. Move `main.bicep` and `bicepconfig.json` into `deploy/bicep/` (co-located with the Bicep sources they govern); move `modules/*` into `deploy/bicep/modules/*` unchanged in internal layout; move `pipelines/azure-pipelines-infra.yml` into `deploy/pipeline/`; move `environments/*.bicepparam` into `deploy/variables/`. Leave `.checkov.yaml` and `ps-rule.yaml` at the repository root, since Checkov and PSRule discover their config by searching from the repo root by default.
- **Rationale**: Matches the four locations the spec explicitly names (FR-001) while keeping each tool's config next to the files it governs or where the tool expects to find it, minimizing path-reference churn beyond what the move itself requires.
- **Alternatives considered**: Keeping `bicepconfig.json` at the repo root — rejected because `az bicep` resolves the nearest `bicepconfig.json` relative to the file being built, and keeping it at the old root would silently stop applying once `main.bicep` moves. Nesting `variables/` under `bicep/` — rejected because the spec names `deploy/variables` as a peer of `deploy/bicep`, and keeping it a peer makes it equally discoverable for both the pipeline and any future non-Bicep tooling that needs environment values.

## 2. Dev/prod parameterization without hardcoded stages

- **Decision**: Introduce one reusable pipeline stage template (`deploy/pipeline/templates/deploy-environment.yml`) that accepts an `environment` parameter (`dev` or `prod`). The main pipeline file instantiates it twice — once per environment — passing the environment name; each instantiation resolves its own `deploy/variables/{environment}.bicepparam` file, targets the Azure DevOps Environment resource named `goat-{environment}`, and (per decision 5) selects a variable group named `goat-ticket-secrets-{environment}`, all via compile-time template parameter substitution (`${{ parameters.environment }}`), which Azure Pipelines resolves before stage expansion.
- **Rationale**: Directly satisfies FR-003/FR-004 — the environment is a single explicit parameter, and stage *logic* is written once, not copy-pasted per environment. Azure DevOps Environment resources (`goat-dev`, `goat-prod`) already exist in the current pipeline and are the natural place to keep the per-environment approval configuration (decision 4) outside the YAML.
- **Alternatives considered**: A single stage with a runtime `${{ parameters.environment }}` loop that deploys both environments in one pass — rejected because it would remove the deliberate dev-then-approve-then-prod promotion sequencing the project currently relies on (prod must never deploy before dev has been exercised in the same run). Making `environment` a queue-time pipeline parameter that a human picks per run, deploying only one environment per run — rejected because it would break the existing promotion flow (dev always precedes prod) without a corresponding request in the spec to change that flow.

## 3. Consolidated "Quality Checks" stage

- **Decision**: Merge Lint, Validate, Security Scan, and What-If into one stage containing a single job with four sequential steps (one per check), each step invoking its own script under `deploy/script/`. The stage runs its Validate/What-If checks against the `dev` variable file as a pre-promotion smoke check — the same target the current, separate Validate/WhatIf stages already use. Each step keeps its own Azure DevOps step-level pass/fail result and log, so a Security Scan failure is distinguishable from a Lint failure without any custom reporting.
- **Rationale**: Satisfies FR-010 (one stage) and FR-011 (individually identifiable results) using only Azure DevOps' native per-step status reporting — no custom aggregation logic is needed. Sequential steps (not parallel jobs) preserve the existing fail-fast ordering (a syntax error should stop before spending time on a security scan or what-if).
- **Alternatives considered**: Four parallel jobs within the one stage — rejected because Lint failing should stop Validate/Security Scan/What-If from running at all (they'd waste a cloud deployment preflight call against code that doesn't even parse), and Azure DevOps jobs run in parallel by default, which would require re-adding explicit `dependsOn` between jobs — equivalent complexity to steps but with more YAML.

## 4. Replacing the custom approval gate

- **Decision**: Delete the `ConfirmProd` stage and its `ManualValidation@0` task entirely. Configure (or, if a prior run already configured it, keep) an Approval check on the `goat-prod` Azure DevOps Environment resource, so any deployment job targeting `environment: goat-prod` automatically pauses for approval before its steps run.
- **Rationale**: Directly satisfies FR-008/FR-009. This also removes the `pool: server` / 4320-minute-timeout workaround the custom task needed, since Environment Approvals are a first-class pause point that doesn't consume agent time while waiting.
- **Alternatives considered**: Keeping `ManualValidation@0` as a secondary, redundant gate alongside Environment Approvals — rejected; the spec requires the custom script's execution to stop being a condition for proceeding (FR-008), not to remain as a belt-and-suspenders check.

## 5. Per-environment secrets without hardcoded suffixes

- **Decision**: Replace the single `goat-ticket-secrets` variable group (with env-suffixed variable names like `ticketQrSigningKeyValueProd`) with two variable groups, `goat-ticket-secrets-dev` and `goat-ticket-secrets-prod`, both exposing the *same* variable names (`ticketQrSigningKeyValue`, `keyVaultCertSecretUri`). The deploy stage template selects the group via `${{ parameters.environment }}` at compile time, so the deployment script always reads the same variable names regardless of which environment is running.
- **Rationale**: This is what makes the deploy script itself environment-agnostic (FR-003/FR-004 apply to configuration values, not just the `.bicepparam` file) — without it, the script would still need an `if prod use X else use Y` branch, which is exactly the hardcoding the spec asks to remove.
- **Alternatives considered**: Keeping one variable group with suffixed names and branching in the script on the `environment` parameter — rejected as it reintroduces the hardcoded per-environment branching FR-003 rules out, just moved from YAML into a script.

## 6. RBAC parent/child decomposition

- **Decision**: `rbac.bicep` becomes a parent module. It declares a `keyVaultPrincipals` array and a `cosmosPrincipals` array (each entry: `principalId`, `roleDefinitionId`, `principalType`) and passes them to two new child modules — `keyVaultRoleAssignments.bicep` and `cosmosRoleAssignments.bicep` — each of which loops over its array with a single `for` resource declaration. The existing Storage- and SQL-account role assignments (`funcToRuntimeStorage`, `funcToBusinessBlob`, `funcToBusinessQueue`, `sqlToRuntimeStorage`) stay as individually named resources directly in the parent module.
- **Rationale**: Matches FR-013/FR-014/FR-015 exactly, which name only Key Vault and Cosmos as the resource types requiring array/for-loop child modules. Storage/SQL assignments differ from each other in role and target per pairing (not a repeated "many principals, one role, one scope" shape), so forcing them into the same array/loop pattern would add indirection without the spec asking for it or the current code exhibiting the duplication problem the array pattern solves.
- **Alternatives considered**: Also converting Storage/SQL assignments into a third array-driven child module for full symmetry — rejected as scope creep beyond FR-013/FR-014; revisit only if a future change actually duplicates storage-assignment resources the way Key Vault/Cosmos assignments are duplicated today.

## 7. Shared network access rules across Storage, Key Vault, and Cosmos

- **Decision**: Add `deploy/bicep/modules/shared/networkAccessRules.bicep` exporting the common *policy intent* (default-deny, Azure-services bypass, optionally an allowed-IP-ranges list) as a reusable object. Storage and Key Vault — which both already accept a literal `networkAcls: { defaultAction, bypass }` object — consume it directly. Cosmos DB, which has no `networkAcls` property (it uses `publicNetworkAccess`, `ipRules`, and `isVirtualNetworkFilterEnabled` instead), maps the same shared object's fields into its own shape locally inside `cosmos.bicep`.
- **Rationale**: Satisfies FR-017 (one shared definition) while respecting FR-018 (resource-specific shape differences stay local). Cosmos's access model is genuinely different at the schema level from Storage/Key Vault's `networkAcls` object — forcing a single literal shared `networkAcls` object onto Cosmos isn't possible without Cosmos silently ignoring unknown properties, which would defeat the "change once, apply everywhere" goal the spec asks for.
- **Alternatives considered**: A shared object shaped exactly like Storage/Key Vault's `networkAcls` and spread (`...`) directly into all three resources — rejected because it would compile for Cosmos but have no effect (Cosmos's ARM schema doesn't have a `networkAcls` property), silently failing SC-007's "applies identically" expectation.

## 8. Deployment slots for App Service and Function App

- **Decision**: Add one `Microsoft.Web/sites/slots@2024-11-01` child resource named `staging` under both `appService` (in `appService.bicep`) and `functionApp` (in `function.bicep`), inheriting the parent plan's compute tier. No slot-swap task, traffic-routing rule, or App Service deployment-slot app-setting divergence is introduced in this change.
- **Rationale**: Satisfies FR-006/FR-007 and matches the spec's own Assumptions section, which scopes this change to provisioning the slot only, leaving swap/cutover automation for a future change.
- **Alternatives considered**: Also wiring the pipeline's deploy scripts to deploy application code into the staging slot and swap — rejected as explicitly out of scope per the spec's Assumptions ("building the actual swap/cutover automation... is explicitly out of scope").

## 9. Extracting inline bash into standalone scripts

- **Decision**: One script per pipeline concern — `lint-bicep.sh`, `validate-deployment.sh`, `preview-changes.sh`, `deploy-environment.sh` — each taking the environment name (and, where needed, the variable-file path and secret values via environment variables already exported by the calling pipeline step) as arguments, under `deploy/script/`. Pipeline steps shrink to a task invocation of the script by path plus any environment-variable exports the script expects.
- **Rationale**: Satisfies FR-019 directly and makes each script independently readable (per the spec's Story 9 acceptance criteria) and independently shell-lintable in the future, without needing the surrounding YAML for context.
- **Alternatives considered**: One monolithic `deploy.sh` with a sub-command per concern (`deploy.sh lint`, `deploy.sh validate`, ...) — rejected as an unrequested abstraction; four small, single-purpose scripts map one-to-one with the four quality checks plus the deploy action, which is simpler to read than a dispatch script with no corresponding requirement asking for it.

## 10. Stage/step display name conventions

- **Decision**: Rename stages/steps to plain English with no abbreviations, tool names, or icons, e.g.: `Lint Bicep` → `Check infrastructure code for syntax errors`; `Validate Against Azure` → part of `Run infrastructure quality checks`; `IaC Security Scan` → (step) `Scan for security issues`; `What-If Preview` → (step) `Preview infrastructure changes`; `Confirm Deploy to Prod?` (removed) → replaced by the Environment Approval's own prompt text; `Deploy to Dev` / `Deploy to Prod` → `Deploy infrastructure to the development environment` / `Deploy infrastructure to the production environment`.
- **Rationale**: Satisfies FR-012 and Story 5's acceptance criteria — understandable without Azure/Bicep/DevOps vocabulary, no icons/symbols.
- **Alternatives considered**: Keeping short technical names but adding a separate plain-English `description` field — rejected; Azure DevOps shows `displayName` prominently in the run UI and timeline, while `description`-style annotations are far less visible to an approver skimming a run, so only renaming the visible name actually satisfies "understandable by non-technical approvers."
